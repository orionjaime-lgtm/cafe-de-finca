# Cambiar la base de datos

**Quién:** los cambios de esquema los hace el responsable de la base (Orión) mediante Pull Request. Si sos otra persona o una IA trabajando en el backend o el frontend y te falta algo, **pedilo** con una descripción: qué columna o tabla, para qué endpoint o pantalla, y qué tipo de dato.

## Pasos para quien hace el cambio

1. Editar `data-base/01-schema.sql` (estructura). Los catálogos van en `02-datos-iniciales.sql` y los datos de prueba en `03-datos-prueba.sql`. Los tres se ejecutan en ese orden.
2. Seguir las convenciones existentes:
   - Nombres en **minúsculas con guiones bajos**, sin comillas.
   - Clave primaria: `INT GENERATED BY DEFAULT AS IDENTITY`.
   - Gramos: `NUMERIC(12,3)`. Dinero: `NUMERIC(12,2)`. Nunca `float`.
   - Agregar `NOT NULL`, `CHECK`, `UNIQUE` e índices en las claves foráneas.
   - Documentar con `COMMENT ON COLUMN`.
3. Si el seed usa fechas, que sean relativas (`CURRENT_DATE - n`).
4. **Los datos de ejemplo no deben romper los `CHECK`**: verificar las cuentas de stock y subtotales.
5. Recrear la base y revisar los errores:
   ```
   docker-compose down -v
   docker-compose up -d
   docker-compose logs db
   ```
   No debe aparecer ninguna línea con `ERROR`.
6. Actualizar la entidad Java correspondiente y correr `./mvnw test`: la prueba `BackendApplicationTests` valida que cada entidad coincida con el esquema.
7. Actualizar el README (sección del modelo de datos) y, si cambia el diagrama, el DER en `docs/`.
8. Pull Request propio, **separado** de otros cambios, y avisar al equipo: todos tienen que recrear su base con `docker-compose down -v`.

## Nunca

- No cambiar el esquema desde Java (`ddl-auto` queda en `validate`).
- No editar la base a mano con SQLTools y olvidarse de pasar el cambio a `01-schema.sql`.
